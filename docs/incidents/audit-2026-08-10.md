## Finding 3 — Migration/provisioning drift

**Result: FAIL.** `contracts/api-specs/migration-manifest.json`'s recorded checksum does
not match the actual file, and is structurally invalid as a sha256 digest.

- `apps/backend/drizzle/` contains exactly one migration file: `0001_init.sql`. Both
  `infra/neon/apply_production.mjs:78` (`manifest.migrationPath`) and
  `infra/neon/provision_pr_branch.mjs:192` (hardcoded relative path) reference it — no
  migration file is referenced-but-missing or present-but-unreferenced.
- Computed this session: `sha256sum apps/backend/drizzle/0001_init.sql` →
  `e2ff5df0de5e47424cd2955ebc61a2ea35064f201bd89dde2ecbe895db36f2a7` (64 hex chars,
  valid sha256 length).
- Manifest value at `contracts/api-specs/migration-manifest.json:5`:
  `a3d8e7c27201c77b334213894c29b27dcb900d71c9014caa834caa974ecdd5fc` — **65 hex
  characters**, one character too long to be any valid sha256 digest, and does not
  match the computed value regardless of length.
- `infra/neon/apply_production.mjs:86-97` (`verifyChecksum()`) runs unconditionally on
  every invocation of that script and throws before connecting to the database if the
  checksum doesn't match. Per `docs/ci-cd-required-secrets.md`, external prerequisite
  #3 (`NEON_PROD_API_KEY`/`NEON_PROD_BRANCH_ID`), this script **has never yet run
  against real production Neon** — meaning the very first production migration apply
  will hard-fail on this mismatch before it can happen, not a live incident yet but a
  guaranteed one on first attempt.
- `.github/workflows/pr-checks.yml:66-97` and `deploy-production.yml:59-76` independently
  re-derive and compare against this same manifest value. Any future PR that touches
  `0001_init.sql` will also fail CI on this same mismatch, independent of whether that
  PR's content is otherwise correct.
